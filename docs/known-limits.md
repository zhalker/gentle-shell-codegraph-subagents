# Known limits

- The frozen-file repair handles only the agent directory Pi uses (`~/.pi/agent`, `$PI_CODING_AGENT_DIR` or `GENTLE_PI_AGENT_HOME`), not `<project>/.pi/agents/`.
- The warm-up has only been measured on local disks, not on a network share. It never kills the processes it starts, because the daemon is shared with your own sessions.
- CodeGraph's own `init` can hang when two start at once, or when a daemon opens the project just after the index is created. The package lock only coordinates sessions sharing the same user temp folder; it cannot prevent access by a terminal, another tool, another user, or Pi's own MCP connection. On Windows, if the session and shell exit before CodeGraph writes its own lock and that takes more than 60 seconds, the package cannot tell that init is still running. The 11-minute stale-lock limit can also expire while a process remains alive.
- The index sync is a background command: a CodeGraph call made right after a session starts can see the previous index. The sync only looks at the directory where Pi starts, not at parents or subfolders. Treat CodeGraph results as navigation hints, not authoritative evidence: they can be stale, incomplete or incorrect; verify findings against source files.
- Two package-started syncs of one project never run at the same time only among the Pi sessions of one user that share the same temp folder on one machine. That lease is not the only writer of the index: `codegraph` run from a terminal, a git hook, another tool, another user, another machine, or Pi's own MCP connection are not seen, so an external sync or index can still run while the package syncs. A successful exit code says that `codegraph sync` finished, not that the index matches the files, and nothing here makes a read during or right after a sync current.
- After a compaction of a parent session the package requests one background sync, but only when the directory where Pi starts already has an index: a compaction never creates one, and a subagent child never requests one. The result is not shown to the session; `synced`, `failed`, `coalesced`, `queued` or a `skipped-` reason (`skipped-no-index`, `skipped-child`, `skipped-coordination-unavailable`) is appended to `~/.pi/agent/codegraph-subagents/sync.log`, one line per request.
- A request that arrives while another session syncs is recorded on disk and served by one follow-up run of that session, and it is only marked as served once that run has finished, so a session killed mid-sync leaves every pending request for the next sync. A session is told `coalesced` only when a run that started after its request completed; until then it says `queued` and the request stays on disk. A lease untouched for 3 minutes (a 2-minute sync plus a margin) is treated as abandoned, so a session whose clock jumps far ahead can be taken over while it runs. When the lease cannot be created, read or gated at all, the package starts no sync and reports `skipped-coordination-unavailable`; that is deliberate, because an uncoordinated run is the failure S2 exists to prevent. Neither coordination sees any of the writers named above, and none of it survives being used from two machines with their own temp folders.
- The lease names the session and the `codegraph` process that session started. A sync that outlives its session (Windows runs the command through a shell, and the command itself can survive a killed Pi) keeps the lease while that process is alive, so the next extension-started sync waits for it instead of overlapping it, and nothing is killed to get there. On Windows the lease trusts the record for up to 60 seconds after the spawn when the shell is gone and CodeGraph's own writer lock does not name the process yet; a process whose pid is reused inside that window could keep a session waiting longer than needed.
- A sync and an init of the same project exclude each other through the package's index lock: the sync takes it for its whole run and records the process it starts, so a compaction that arrives during an init is kept and served once the init ends (it waits, and says `queued` if the init outlasts it). This is still cooperation between the package's own sessions only: an init or a sync started by another tool is not ordered by it.
- A startup sync that was coalesced into another session's run still warms this session's daemon, while that other session may still be syncing. The warm-up is a read through the project's daemon, not a sync, and the package makes no claim about what that read can touch.
- Asking the daemon directly relies on two internal details of CodeGraph: the registry in `~/.codegraph/daemons/` and the hello line with `protocol: 1`. If either changes, or the daemon answers anything unexpected, the explorer adds nothing and the warm-up starts in the background instead. A daemon that does not say hello within 2 s gives way to the next registered one, and a daemon that is there but does not answer within 10 s is not retried.
- A background warm-up started by a child dies with that child, so a child that ends within about 3 s warms nothing; the daemon warm-up of a session start is awaited and keeps its own 120 s limit.
- The system-prompt rule and the exploration reminder read the child's declared tool list from `GENTLE_PI_AGENTS_CHILD=1` and `GENTLE_PI_AGENTS_REQUESTED_TOOLS`; this declaration does not prove that the MCP tool actually connected. A child without those launcher variables gets no section and no reminder. The shell check behind the reminder is a word match on the command line, so an unusual search command can be missed (the reminder is advisory and never blocks a call). The reminder budget is in memory: it is once per session, starts over after a compaction, and starts over after a reload.
- The package does not add `mcp__codegraph__codegraph_explore` to any agent file. A gentle-shell version whose agent assets lack the tool leaves that agent without it until gentle-shell is upgraded; this package only reports the missing MCP server or exposure.
- The `codegraph` MCP server has to be configured or registered by an extension; the package never creates it. When Pi is launched from a GUI or service, its `PATH` may differ from your shell. An absolute MCP server command can fix the server launch, but this package's `init` and `sync` still need `codegraph` on Pi's `PATH`.
- The package never writes an agent file or `mcp.json`. When the CodeGraph server is missing, or `codegraph_explore` is not exposed directly to subagents, the session warns at startup but nothing is changed: the fix is your edit to `mcp.json` (or the extension that registers the server). No backup is written any more; a `*.pre-codegraph-subagents.bak` left by a version up to 0.9.x is never modified and still identifies a file that version froze.
- Tested with Pi 1.4.0 and node 24.
- The post-`init` hook sees the native `codegraph` tool only. `codegraph init` typed into `bash`, run in a terminal, by a git hook or by another tool is not observed, so no sync is requested for it and nothing is appended to that call. The hook's own append is bounded to 10 s: a sync that has not come back by then is reported as `pending` (explicitly not confirmed current) and its final outcome, `init-sync-<outcome>`, goes to `sync.log` when it settles. A sync request that is still pending when Pi exits stays on disk and is served by the next package-started sync of that project, as every other request is.
- The role of a subagent child is inferred from the tool list gentle-pi requested for it, because no agent name is passed. A read-only role is "a command tool, no file-writing tool": verify and the judges today. An agent whose tool list changes shape can be classified differently — notably, a read-only agent without `bash` looks like the explorer and may get a post-init sync. Agent files are never rewritten to enforce a role, so a tool a user added to verify stays; the package simply starts no index write for that role.
- The daemon status comes from the CodeGraph daemon registry only. An MCP server entry therefore proves nothing about reachability, and a live daemon is used even with no MCP server configured. A live record whose daemon hangs is reused (one read, bounded by the warm-up timeout) and never doubled by a second server; a stale registry record whose pid was reused by another process can look live until its socket is gone. Nothing here stops a daemon, and the package never writes to the daemon registry.
- The session-wide worktree seeding takes each worktree's index lock before copying, but the copy itself is not ordered against a writer outside this package (a terminal `codegraph init`, another tool, another machine), and it still copies only the `codegraph.db` when the main index is at rest according to the package's own lock and CodeGraph's writer lock.
- A read-only role starts no index write, so a verify or judge child handed an unindexed worktree gets none until a writer or a session prepares it. That is deliberate: those roles must not initiate `init` or `sync`.
