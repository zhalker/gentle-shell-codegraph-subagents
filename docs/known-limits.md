# Known limits

- Only the global agent directory is handled, not `<project>/.pi/agents/`.
- The warm-up has only been measured on local disks, not on a network share. It never kills the processes it starts, because the daemon is shared with your own sessions.
- CodeGraph's own `init` can hang when two start at once, or when a daemon opens the project just after the index is created. The package lock only coordinates sessions sharing the same user temp folder; it cannot prevent access by a terminal, another tool, another user, or Pi's own MCP connection. On Windows, if the session and shell exit before CodeGraph writes its own lock and that takes more than 60 seconds, the package cannot tell that init is still running. The 11-minute stale-lock limit can also expire while a process remains alive.
- The index sync is a background command: a prefetch that runs before it finishes can see the previous index. The sync only looks at the directory where Pi starts, not at parents or subfolders. Treat prefetched results as navigation hints, not authoritative evidence: they can be stale, incomplete, truncated or incorrect; verify findings against source files.
- Two package-started syncs of one project never run at the same time only among the Pi sessions of one user that share the same temp folder on one machine. That lease is not the only writer of the index: `codegraph` run from a terminal, a git hook, another tool, another user, another machine, or Pi's own MCP connection are not seen, so an external sync or index can still run while the package syncs. A successful exit code says that `codegraph sync` finished, not that the index matches the files, and nothing here makes a read during or right after a sync current.
- After a compaction of a parent session the package requests one background sync, but only when the directory where Pi starts already has an index: a compaction never creates one, and a subagent child never requests one. The result is not shown to the session; `synced`, `failed`, `coalesced`, `queued` or a `skipped-` reason (`skipped-no-index`, `skipped-child`, `skipped-coordination-unavailable`) is appended to `~/.pi/agent/codegraph-subagents/sync.log`, one line per request in the same format as `prefetch.log`.
- A request that arrives while another session syncs is recorded on disk and served by one follow-up run of that session, and it is only marked as served once that run has finished, so a session killed mid-sync leaves every pending request for the next sync. A session is told `coalesced` only when a run that started after its request completed; until then it says `queued` and the request stays on disk. A lease untouched for 3 minutes (a 2-minute sync plus a margin) is treated as abandoned, so a session whose clock jumps far ahead can be taken over while it runs. When the lease cannot be created, read or gated at all, the package starts no sync and reports `skipped-coordination-unavailable`; that is deliberate, because an uncoordinated run is the failure S2 exists to prevent. Neither coordination sees any of the writers named above, and none of it survives being used from two machines with their own temp folders.
- The lease names the session and the `codegraph` process that session started. A sync that outlives its session (Windows runs the command through a shell, and the command itself can survive a killed Pi) keeps the lease while that process is alive, so the next extension-started sync waits for it instead of overlapping it, and nothing is killed to get there. On Windows the lease trusts the record for up to 60 seconds after the spawn when the shell is gone and CodeGraph's own writer lock does not name the process yet; a process whose pid is reused inside that window could keep a session waiting longer than needed.
- A sync and an init of the same project exclude each other through the package's index lock: the sync takes it for its whole run and records the process it starts, so a compaction that arrives during an init is kept and served once the init ends (it waits, and says `queued` if the init outlasts it). Only an init makes the explorer skip its prefetch; a sync of an existing index does not. This is still cooperation between the package's own sessions only: an init or a sync started by another tool is not ordered by it.
- A startup sync that was coalesced into another session's run still warms this session's daemon, while that other session may still be syncing. The warm-up is a read through the project's daemon, not a sync, and the package makes no claim about what that read can touch.
- Asking the daemon directly relies on two internal details of CodeGraph: the registry in `~/.codegraph/daemons/` and the hello line with `protocol: 1`. If either changes, or the daemon answers anything unexpected, the explorer adds nothing and the warm-up starts in the background instead. A daemon that does not say hello within 2 s gives way to the next registered one, and a daemon that is there but does not answer within 10 s is not retried.
- A background warm-up dies with the explorer child that started it, so a child that ends within about 3 s warms nothing; a real explorer session lasts much longer. The 10 s prefetch limit was chosen from measured answers up to 8375 ms on a network share, and the daemon warm-up of a session start is awaited and keeps its own 120 s limit.
- The explorer prefetch requires the launcher to set `GENTLE_PI_AGENTS_CHILD=1` and `GENTLE_PI_AGENTS_REQUESTED_TOOLS` to the child's declared comma-separated tool list. It recognizes a read-only child with the CodeGraph MCP tool and no writing tools; this declaration does not prove the MCP tool actually connected. Without these launcher variables the prefetch is skipped. The first 300 sanitized characters of the task become the query, so verbose instructions can broaden the result; the returned context is capped at 12,000 characters.
- The rewrite of the explorer's own instructions matches known sentences; if gentle-pi rewords them, they are left as they are.
- The `codegraph` MCP server has to be configured or registered by an extension; the package never creates it. When Pi is launched from a GUI or service, its `PATH` may differ from your shell. An absolute MCP server command can fix the server launch, but this package's `init` and `sync` still need `codegraph` on Pi's `PATH`.
- Tested with Pi 1.4.0 and node 24.
